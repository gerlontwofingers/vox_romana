F. Editor — Chunk Review & Retry Flow
---------------------------------------
- The Editor reviews each completed chunk synchronously before the Conductor
  advances to the next chunk.
- The Editor's review lens (not exhaustive — use judgment):
    1. Speaker clarity  — Can the audience tell who is speaking at all times?
    2. Repetition       — Has this been said before? Is it adding value?
    3. Intention fidelity — Does this chunk serve the prompt and the outline?
    4. Instruction compliance — Are all specific instructions being followed?
    5. Factual accuracy — Optionally, consult the FactChecker on specific
                          claims if the Editor has doubts.
    6. Narrative quality — Is this engaging? Does it advance the show?
- On PASS: Conductor proceeds to the next chunk. Editor logs a compact note.
- On FAIL: Editor writes detailed rejection notes explaining exactly what is
  wrong. Notes flow THROUGH the chain of command (Editor → Conductor →
  Director → cast) so the redo has full context at every level. The whole
  chunk is regenerated from scratch — not patched.
- max_retries is configurable (default: 3). After exhausting retries, the
  Conductor publishes the best available attempt WITH a warning flag in the
  output JSON and a summary of the Editor's unresolved objections.
- The Editor is NOT interactive and does NOT block for human input. It decides
  and moves on.
- The Editor may call the FactChecker at any point during its review.
  Otherwise the FactChecker operates normally in the research pipeline.


G. Editor Notes — Archival & Memory
-------------------------------------
- ALL Editor notes are preserved — passes, fails, and partial-redo notes.
- Notes must be COMPACT but DETAILED ENOUGH TO BE USEFUL. The audience for
  these notes is the next Conductor and the next Editor. Write for them.
  Good note: "Round 2 opened with both speakers restating their round 1
  positions almost verbatim. Accepted on retry 2 after injecting a
  wildcard pivot beat."
  Bad note: "Repetitive. Redone."
- Notes accumulate across broadcasts and will grow over time.
  Compaction policy: keep the last 10 broadcasts verbatim; for everything
  older, the Librarian (see section K) or an offline job summarizes them
  into a rolling "patterns" summary stored alongside the raw archive.
  The session-start note injection must never exceed a defined token budget
  (configurable; suggested default: ~600 tokens).
- At the START of each new broadcast, the Conductor and Editor each receive
  a Librarian-assembled summary of relevant past notes, within the token
  budget, so they can be mindful of recurring issues and successful patterns.
- Notes are stored in the studio memory layer (persistent JSON/JSONL).
  Outline version snapshots are stored alongside them for traceability.
- Note schema (minimum fields):
    broadcast_id, chunk_id, outline_version, status (pass|fail|warn),
    attempt_number, summary, issues[], recommendations[]


H. Speaker Clarity & Radio-Style Dialogue
-------------------------------------------
- Historical problem: It is often impossible to tell which character is
  speaking from the generated text alone. In visual/audio media, camera cuts
  and mixing do this work; in pure text and TTS, we must do it explicitly.
- All agents should prefer explicit speaker identification:
    - Speaker tags at line start: "Alex:", "Host:", "MORGAN (skeptical):"
    - Scene direction stingers between speakers or chunks:
      "Announcer (V.O.):", "[Cut to field reporter]"
    - Bracketed audio/action cues to signal transitions:
      "[theme music]", "[applause]", "[door slam]"
- Inspiration: old radio broadcasting conventions — announcer lead-ins,
  clear handoffs, sonic markers. Every transition should be audible.
- Editor behavior on speaker ambiguity: do NOT merge ambiguous lines. Mark
  the chunk as "requires speaker disambiguation", specify exactly which lines
  are unclear, and suggest concrete label insertions in the redo notes.


I. Shared Core Resources & Extensibility
------------------------------------------
- The codebase already separates show-agnostic infrastructure (core/) from
  show-specific logic (shows/debates/, shows/news/). PRESERVE THIS.
- New capabilities — Editor, Chunker, retry loop, outline versioning,
  FactChecker interface — belong in core/ or a new core/editing/ sub-module
  so all show types can use them.
- Future show types (e.g., audiobook) plug into the shared core and add a
  shows/audiobook/ module. They inherit the Editor, outline, and retry
  machinery automatically.
- Do not duplicate logic across show types. If something is general, it goes
  in core/.


J. Implementation Safety Guidelines
-------------------------------------
- Extend existing dataclasses (e.g., DirectorBrief) rather than replacing
  them. Add new fields as Optional with sensible defaults so existing tests
  remain green.
- The existing _director_note / check_interval pattern in DebateConductor is
  the seed of the new Director outline broadcast. Evolve it, don't rewrite it.
- max_retries must be a config field, not a hardcoded constant.
- Persistent agent sessions should wrap the existing LLM client and accumulate
  message history in a list; this is a thin layer over existing client code.
  Apply sliding-window compression to ALL persistent sessions (not just the
  Conductor). Window size K and summary token budget are config fields.
- Keep all changes reversible at the module level: feature-flag new behavior
  where possible so the old pipeline still runs without the Editor.
- The Librarian is always ephemeral. Never give it a persistent session.
  It reads from the archive store and returns structured results — that is
  its entire job. This keeps the archive access pattern clean and auditable.


K. Librarian — Searchable Historical Archive
----------------------------------------------
- Purpose: Any persistent agent (Conductor, Editor, Director, cast member)
  may at any time ask the Librarian to search the historical notes archive.
  The Librarian handles retrieval, relevance filtering, and formatting so
  the querying agent receives an answer it can immediately act on.
- Lifecycle: EPHEMERAL. The Librarian is spun up on demand, performs its
  query, returns structured results to the calling agent, and is discarded.
  It has no memory of its own and carries no session state.
- Query interface: the calling agent sends a natural-language query plus
  optional filters (show_type, date_range, chunk_type, status). Example:
    "Find all Editor rejections on debate rounds where speakers were
     flagged for repetition in the last 5 broadcasts."
- Result format: the Librarian returns a compact, structured summary the
  calling agent can inject into its own context. It should:
    - Rank results by relevance to the query
    - Strip redundant metadata; keep only what's useful
    - Respect the caller's token budget (passed as a parameter)
    - Flag if no relevant records were found
- Search strategy: keyword + metadata filter first (fast, cheap); fall back
  to LLM-assisted semantic matching if keyword search returns nothing useful.
  The archive is JSON/JSONL — no external vector DB required initially.
  Add vector indexing only if search quality proves insufficient.
- Typical callers and use cases:
    Conductor at session start → "What recurring issues should I watch for
                                   with this topic/format?"
    Editor during review       → "Has this specific failure pattern appeared
                                   before? What fixed it?"
    Director at outline build  → "What outline structures worked well for
                                   this show type in the past?"
- The Librarian lives in core/ (not tied to any show type). All show types
  share the same archive and the same Librarian.
